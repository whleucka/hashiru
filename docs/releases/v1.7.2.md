# v1.7.2

Patch release. First boot stops flooding the screen, the log it hides behind
gets commands to reach it, and the install stops compiling things nobody asked
for.

## Quiet installs

- `HASHIRU_QUIET` keeps child-process output — pacman transactions, makepkg
  builds, git clones — in the install log instead of on the console, behind a
  single progress line: stage counter, bar, percentage, live clock, and what
  the current stage is doing.
- Defaults to whatever `HASHIRU_UNATTENDED` is. On for the ISO's first boot,
  where the flood is the whole problem and nobody is reading it; off for manual
  runs, where that output is what you debug against. Force either way from
  `hashiru.conf`.
- The console gets its own file descriptor (fd 3), so redirecting a stage's
  stdout into the log no longer takes the log lines with it.
- Only draws on a real terminal. A pipe, a redirect or CI degrades to the
  ordinary line-oriented output — no escape sequences ever reach a file.
- Warnings and errors still print as they happen, over the cleared bar.
- Progress granularity is limited to what is actually known: stage count, and
  the AUR loop's package index. A pacman transaction covers a whole manifest at
  once, so it contributes a label and no fraction.

## Seeing what happened

- `hashiru log [-f]` — pages the install log, opening at the end; `-f` follows
  it live.
- `hashiru report` — the warnings digest. Checks the archived copy too, which is
  where `/etc/profile.d/hashiru-report.sh` moves it after showing it once at
  login; until now the digest was unreachable after that.
- A failed stage dumps the last 40 log lines to the console. Without it a failed
  unattended install showed a progress bar and nothing else, which is worse than
  the flood being fixed.
- The completion banner names the warning count, so an unattended run that
  finished with AUR packages missing no longer reads like a clean one.

## First boot

- The bootstrap writes to `/dev/tty1` directly, so the progress line draws on
  the screen and the journal is not filled with carriage returns. Same
  `[[ -w /dev/tty1 ]]` guard as the banner — serial and headless boots are
  unaffected and fall back to plain log lines.
- Stage detail no longer reaches the journal; it is all in
  `~/.local/share/hashiru/install.log`. The wrapper's own `==>` and `!!` lines
  still go there, which is what debugging a failed first boot as root before any
  login needs.
- The banner and the failure message name the log file.

## Install time

- AUR packages install in one batched `yay` call, falling back to the existing
  one-at-a-time loop only when that fails. A stock `aur.txt` paid a separate
  dependency resolution and a separate `--removemake` cycle for every package,
  over largely the same build dependencies; the common case now pays one of each.
- Nothing about failure isolation changes. A flaky build still can't abort the
  bootstrap, still lands in the warnings digest, and the stage still exits
  clean — that just isn't paid for when there is nothing to isolate.
- `sherlock-confetti` is out of `aur.txt`. It was the only significant compile
  on the critical path — a cargo build on every fresh install — and it made a
  fresh install pull two Rust toolchains, since it makedepends on `rust` while
  stage 99 runs `rustup default stable`. `update-system` guards the call, so a
  machine without it just gets no confetti.
- `sqls` is out too: a Go build on every fresh install, for a SQL language
  server nothing in this repo configures. Install it by hand if an editor config
  wants it.
- What remains in `aur.txt` is two npm shims, a prebuilt binary, a binary repack
  and one small C build. Downloads were already tuned (`ParallelDownloads = 10`
  and reflector mirror-ranking, both before the first `-Syu`), so batching plus
  those two removals is the headroom that was actually there. Measured in a VM:
  the bootstrap reached stage 4 of 9 in the time it used to spend still
  compiling at stage 3.

Neither removal uninstalls anything. Machines that already have those packages
keep them; they just stop being part of what a new machine is.

## Provenance

- `/etc/hashiru-release` records `HASHIRU_VERSION` from `git describe --tags`
  alongside the commit, and `hashiru status` leads with it. `v1.7.2-3-gabc1234`
  answers "which Hashiru is this" in a way twelve hex characters never did.
- `hashiru update` stamps the same field, so an update no longer drops it.
- `hashiru changelog [tag]` reads `docs/releases/`, newest first — the same
  files CI already uses for release bodies. Accepts `v1.7.2` or `1.7.2`.
- `doctor` reports the version too, falling back to the commit on machines
  stamped before the field existed.

## Fixes

- `update-system` guards `paplay` and `confetti` with `command -v`, so an update
  no longer ends on a command-not-found for the sake of an animation.
- `iso/build.sh` warns when the ref it is about to pin exists on no remote
  branch. The pin is resolved on the *target* machine, which clones from GitHub
  — an unpushed commit fails the install, not the build, which is an expensive
  place to find out.
- `iso/test-qemu.sh` names `qemu-desktop` rather than `qemu-base`; `-display
  gtk` needs the gtk UI module, which `qemu-base` does not carry.

## Upgrading

`hashiru update`. Quiet mode, the new commands and the version stamp land
immediately. The first-boot changes are baked into the ISO and only affect new
installs; the `aur.txt` removals affect new installs only.
