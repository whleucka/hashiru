# v1.7.2

Patch release. First boot stops flooding the screen, and the log it hides
behind gets two commands to reach it.

## Quiet installs

- `HASHIRU_QUIET` keeps child-process output — pacman transactions, makepkg
  builds, git clones — in the install log instead of on the console, behind a
  single progress line: stage counter, bar, percentage, live clock, and what
  the current stage is doing.
- Defaults to whatever `HASHIRU_UNATTENDED` is. On for the ISO's first boot,
  where the flood is the whole problem and nobody is reading it; off for manual
  runs, where that output is what you debug against. Force either way from
  `hashiru.conf`.
- The console gets its own file descriptor (fd 3), so redirecting a stage's
  stdout into the log no longer takes the log lines with it.
- Only draws on a real terminal. A pipe, a redirect or CI degrades to the
  ordinary line-oriented output — no escape sequences ever reach a file.
- Warnings and errors still print as they happen, over the cleared bar.
- Progress granularity is limited to what is actually known: stage count, and
  the AUR loop's package index. A pacman transaction covers a whole manifest at
  once, so it contributes a label and no fraction.

## Seeing what happened

- `hashiru log [-f]` — pages the install log, opening at the end; `-f` follows
  it live.
- `hashiru report` — the warnings digest. Checks the archived copy too, which is
  where `/etc/profile.d/hashiru-report.sh` moves it after showing it once at
  login; until now the digest was unreachable after that.
- A failed stage dumps the last 40 log lines to the console. Without it a failed
  unattended install showed a progress bar and nothing else, which is worse than
  the flood being fixed.
- The completion banner names the warning count, so an unattended run that
  finished with AUR packages missing no longer reads like a clean one.

## First boot

- The bootstrap writes to `/dev/tty1` directly, so the progress line draws on
  the screen and the journal is not filled with carriage returns. Same
  `[[ -w /dev/tty1 ]]` guard as the banner — serial and headless boots are
  unaffected and fall back to plain log lines.
- Stage detail no longer reaches the journal; it is all in
  `~/.local/share/hashiru/install.log`. The wrapper's own `==>` and `!!` lines
  still go there, which is what debugging a failed first boot as root before any
  login needs.
- The banner and the failure message name the log file.

## Upgrading

`hashiru update`. Quiet mode and both new commands land immediately; the
first-boot changes are baked into the ISO and only affect new installs.
